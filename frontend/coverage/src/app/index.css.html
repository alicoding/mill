/* Genuinely global styles only: design tokens, the html/body reset, and the
   app's own flex-column layout root. Per-view visual styling lives in each
   component's own *.module.css (Primer React v38's own guidance:
   https://github.com/primer/react/discussions/7086 -- "prefer to use CSS
   modules over styled-components and css variables over javascript
   theming"). Imported once from main.tsx so Vite's own pipeline processes
   it (hashed filename, minification, HMR) instead of the previous raw
   <link> tag in index.html, which bypassed all of that. */
 
:root {
    /* Golden-ratio spacing scale (φ ≈ 1.618), used for the vertical rhythm.
       Mill's own supplementary scale, not a color token -- Primer has no
       equivalent to adopt here, unlike everything below this comment used
       to be (see App.tsx's color-mode effect for why html/body can use
       Primer's real --bgColor-default/--fgColor-default tokens directly
       now instead of a second, hardcoded color source that silently
       stopped matching the theme the moment light mode became real). */
    --s-2: 1rem;
    --s-3: 1.618rem;   /* φ   */
    --s-4: 2.618rem;   /* φ²  */
    --s-5: 4.236rem;   /* φ³  */
 
    font-family: -apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, "Helvetica Neue", Arial,
        sans-serif, "Apple Color Emoji", "Segoe UI Emoji";
    /* NOT set here -- App.tsx's color-mode effect sets this dynamically
       from Primer's own resolvedColorMode (light/dark, with 'auto'
       already settled by Primer's system-preference detection), since a
       static value would force native browser chrome (scrollbars, form
       control rendering) into the wrong scheme half the time once light
       mode is a real, user-selectable option. */
    -webkit-font-smoothing: antialiased;
    -moz-osx-font-smoothing: grayscale;
    -webkit-text-size-adjust: 100%;
}
 
/* Mill's own accent + node-kind + mono tokens live in mill-tokens.css,
   imported from main.tsx AFTER @primer/primitives' theme CSS
   (deliberately, not here) -- see that file's header comment for why
   this needed a real separate file rather than living in this one. */
 
* { box-sizing: border-box; }
 
html {
    background: var(--bgColor-default);
    /* Matches Wails' own documented pattern for killing overscroll bounce:
       https://wails.io/docs/guides/overscroll/ */
    height: 100%;
    overflow: hidden;
}
html, body {
    margin: 0;
    color: var(--fgColor-default);
}
body {
    height: 100%;
    overflow-x: hidden;
    /* Nothing in the chrome is selectable (it's an app, not a document); the
       Spec view opts back in for its own content. */
    -webkit-user-select: none;
    user-select: none;
    /* Drag the window by its background. Interactive controls opt out with
       --wails-draggable: no-drag (the property inherits). */
    --wails-draggable: drag;
}
 
/* Primer's ThemeProvider/BaseStyles wrap #root in their own plain <div>s
   (verified by walking the live DOM, not assumed) that default to
   display:block -- so body's own flex-column layout can't reach through
   them to lay out nav/view/footer as siblings. Rather than chasing that
   vendor-owned markup with display:contents (fragile: a future Primer
   version could add/remove wrapper divs and silently break it again),
   App.tsx owns an explicit .app-shell div as its actual layout root.
   height uses viewport units, not %, because percentage heights need
   every ancestor in the chain to have a definite height, and the Primer
   wrapper divs above don't -- confirmed by stress-testing with 200
   paragraphs of dummy content before landing this: with % or min-height,
   the whole page grew to fit the content and the footer scrolled 7000px
   away instead of the flex:1;min-height:0 pane below clipping internally.
   Plain global class, not a CSS module, since App.tsx is the one place
   that needs it and it's structural chrome rather than view content.
 
   No horizontal/top padding here, deliberately -- a real, reported bug
   (a visible gap between the window's left edge and the sidebar) traced
   to exactly this: golden-ratio padding applied around the *whole* shell
   (PageLayout.Sidebar included) rather than the content region alone, no
   real app insets its own sidebar from the window edge this way. Every
   region already supplies its own inset independently: PageLayout.Sidebar
   has its own `padding="condensed"` prop, PageLayout.Content's children
   get theirs from shared/PageContainer.tsx, .footer (App.module.css) sets
   its own padding directly -- this outer layer was pure double-padding on
   top of those, stacking with each page's own PageContainer padding to
   produce the reported "way too much dead space" symptom. Safe-area
   insets (notch / home indicator) are the one thing no inner region
   owns, so those alone stay here. */
.app-shell {
    height: 100vh;
    height: 100dvh;
    display: flex;
    flex-direction: column;             /* titlebar band + content area + footer, top to bottom */
    padding: env(safe-area-inset-top) env(safe-area-inset-right) 0 env(safe-area-inset-left);
    /* Single source of truth for the sidebar column's width -- shared by
       the real PageLayout.Sidebar element (App.module.css's `.sidebar >
       :first-child`) and the titlebar band's own left segment
       (App.module.css's `.titlebarLeft`), so the two can never visually
       drift apart. This is the fix for the reported flaw: the titlebar
       band used to ignore the sidebar column entirely (a fixed
       traffic-light inset, tabs floating over the nav rail, nothing
       moving when the rail collapsed) because Chrome's tabs-in-titlebar
       pattern assumes no sidebar at all -- Slack/VS Code's own
       shape (band hands its left edge off to the sidebar column) is the
       correct reference once one exists. App.tsx flips
       `data-sidebar-open` on this element; 256px pins Primer's own
       `--pane-width-small` default explicitly rather than re-deriving it
       twice -- checked directly against PageLayout's compiled CSS, that
       token itself varies by breakpoint (240px at >=768px, 256px at
       >=1012px, 100% below that), and Mill's desktop window lives well
       above that breakpoint in practice, so one fixed number both
       consumers can share beats two independent responsive reads landing
       on different values. 52px matches the sidebar's existing collapsed
       icon-rail width. */
    --mill-sidebar-width: 256px;
}
.app-shell[data-sidebar-open="false"] {
    --mill-sidebar-width: 52px;
}
 
/* The titlebar band itself (App.tsx's own .titlebar/.titlebarNative,
   App.module.css) is a real flex child of .app-shell, rendered first --
   not a padding reservation on .app-shell. Previously this was a
   .app-shell--native-titlebar padding-top:38px rule reserving empty
   space above the content for the macOS hidden-inset traffic lights;
   superseded by the Chrome-style tabs-in-titlebar band, which now
   occupies that space as a real, always-present element (the work-tab
   strip lives there) rather than blank padding. */
 
/* Scrollable content pane -- since the PageLayout sidebar migration
   (docs/SPEC.md §2.2), applied only to PageLayout.Content (App.module.css)
   rather than separately on every view's own root: one scroll region, not
   an accidental nested pair. flex:1 1 auto;min-height:0 alone was enough
   when this sat directly in .app-shell's own flex column; now that its
   parent is a flex-direction:row container (PageLayout's internal
   Sidebar+Content row), flex-grow there sizes width, not height -- height:
   100% forces the actual height once App.module.css's PageLayout overrides
   give that parent a real, resolved height to inherit from (see the fuller
   explanation there). */
.view-pane {
    flex: 1 1 auto;
    min-height: 0;
    height: 100%;
    overflow-y: auto;
}
 
/* For Composition's tab bar (CompositionView.tsx): Primer's <Tabs>
   renders no wrapping element of its own, so the tab strip and the
   active TabPanel land as direct siblings, not a single child -- they
   need a flex-column parent so a fill-height TabPanel grows into only
   what's left after the tab strip, not the tab strip's own height on
   top. That parent is NOT .view-pane itself, though -- confirmed
   directly by inspecting the live DOM, not assumed: Primer's
   PageLayout.Content renders an extra internal wrapper div between the
   element .view-pane's className actually lands on (a "ContentWrapper")
   and the real content -- className support in Primer's own component
   stops one level higher than where the app's content actually renders.
   Targeted structurally (.view-pane's only child), same "don't chase
   vendor-owned hashed class names" precedent as App.module.css's
   `div:has(> main.view-pane)` rule for the Sidebar+Content wrapper one
   level up. Harmless for every other page (Runbook/Activity/Spec each
   render exactly one child here already, so a flex column with one item
   behaves identically to block). */
.view-pane > div {
    height: 100%;
    min-height: 0;
    display: flex;
    flex-direction: column;
}
 
/* Primer portals every Dialog/overlay into #__primerPortalRoot__
   (its own stable id), whose wrappers each carry inline z-index:1 --
   without a z on the ROOT, app chrome (titlebar, toolbar, the
   boards' controls and edge labels at z 1000) paints straight over
   any open dialog. One z here lifts the whole overlay layer above
   chrome while dialogs keep their natural DOM-order stacking among
   themselves (a confirm opened from a page stays above that page). */
#__primerPortalRoot__ {
    z-index: 1200;
}
